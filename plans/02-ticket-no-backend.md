# PLANO 02: Ticket do WebSocket gerado e assinado pelo backend (Ed25519)
Status: concluído (validação manual pendente em make dev/VM)
Objetivo: o gameServer deixa de ter qualquer segredo de JWT: o backend valida o login e assina o ticket com chave privada Ed25519, e o gameServer só confere o ticket com a chave pública.
Fora do escopo: refresh do login e claims de IP/navegador (plano 03); mudar o formato do ticket que o cliente recebe (`data.ticket` segue igual); trocar o JWT de login do backend para assimétrico; validar no backend se o jogador pode entrar na sala (continua no `GetTicket` do gameServer).
Premissas e decisões: Clientes: não se aplica (repo sem `task clientes`; módulos tocados: backend, gameServer, client/tests, k8s) · assinatura Ed25519 via `jwt.SigningMethodEdDSA` do golang-jwt já instalado (sem dependência nova) · formato das chaves: base64 do PEM numa linha só (privada PKCS8: `openssl genpkey -algorithm ed25519 | base64 -w0`; pública PKIX: `openssl pkey -pubout | base64 -w0`); o código faz `base64.StdEncoding.DecodeString` → `pem.Decode` → parse, e falha na subida se faltar ou for inválida (sem imprimir o valor) · envs novas: backend `TICKET_PRIVATE_KEY` e `TICKET_EXPIRATION` (horas, padrão 2); gameServer `TICKET_PUBLIC_KEY` · os `.env.example` trazem um par de dev válido (gerado no T1), senão o `make dev` não sobe · saem do código do gameServer `JWT_SECRET`, `BACKEND_JWT_SECRET` e `JWT_EXPIRATION` · `GAME_JWT_SECRET` deixa de ser usado pelo chart, mas continua no `.env.production` e no Secret nesta entrega (rollback do `helm --atomic` volta para a imagem antiga, que precisa dele); remover num deploy seguinte · separação de tokens: login HS256 com `aud: "hoodwink-login"`, ticket EdDSA com `aud: "hoodwink-ticket"`; cada parser usa `jwt.WithValidMethods` com o seu algoritmo e `jwt.WithAudience` com a sua audiência (ticket nunca vale como login e vice-versa; `alg: none` recusado) · token de login antigo sem `aud` continua aceito pelo backend até vencer (`exp` de 24h); só o ticket exige `aud` desde já · claims do ticket com as MESMAS tags json de `ClaimsHoodwink` (`playerId`, `username`, `roomId`, `exp`) para não mexer no WebSocket · contrato interno (só a API key `x-api-key` existente, comparada com `subtle.ConstantTimeCompare`): `POST /internal/validateToken` {token} → 200 `{id, username}` | 401 `{message}`; `POST /internal/tickets` {token, roomId} → 200 `{ticket}` | 400 roomId vazio | 401 token inválido/vencido/temp · o backend revalida o token com o `JWTService` atual (HS256, `JWT_SECRET`), lê `temp` com comma-ok e não consulta o banco (igual ao middleware de hoje) · `/internal/*` nunca é publicado: o nginx da borda responde 404 em `location ^~ /api/internal/` · gameServer: erro de rede, timeout (3s) ou 5xx do backend → 503 "Servidor de login indisponível"; 401 do backend → 401 ao cliente · `JWTService` do gameServer perde `GenerateToken` e o parâmetro `useBackendSecret`; o middleware põe `ClaimsBackend{Id, Username}` no contexto (mesma chave `contextKeys.PlayerContextKey`) · o agente não faz push em `production` nem roda nada na VM: passos na VM ficam marcados "(manual)" no aceite · testes geram o par com `ed25519.GenerateKey(rand.Reader)` em runtime, sem fixture em disco · Revisado em 2026-11-07: 14 correções aplicadas.
Pré-requisitos: `openssl` para gerar o par de dev; `make dev` (Postgres + Redis) para o T5; acesso do dono à VM para o `.env.production` e o `edge-nginx.sh`

## Riscos
- Deploy fora de ordem (gameServer novo, backend velho) quebra a entrada nas salas → os dois saem no mesmo `helm upgrade --atomic`; chaves no `.env.production` ANTES do push (aceite manual)
- Rollback do `--atomic` volta a imagem antiga → `GAME_JWT_SECRET` fica no Secret nesta entrega
- Uma chamada a mais ao backend em cada `/getTicket` e `/newRoom` → localhost na VM (hostNetwork); timeout de 3s
- API key de dev é UUID zerado no seed → só vale em local; produção usa a gerada pelo `init-secrets.sh`, e `/internal/*` não sai pelo nginx

# PLANO 04: Coletor de requests com tela de super-admin
Status: concluído (validação manual pendente em make dev/VM)
Objetivo: toda request HTTP do backend e do gameServer fica gravada no Postgres e um super-admin consulta numa tela simples, filtrando por rota, período, status e usuário.
Fora do escopo: mensagens de WebSocket (só o upgrade `/game` entra); gráficos e métricas agregadas; exportar CSV; tela para promover admin (é via SQL); arquivo fora do banco (S3/disco).
Premissas e decisões: Clientes: não se aplica (repo sem `task clientes`; módulos tocados: backend, gameServer, client/web, k8s) · decisões do usuário: coletar HTTP dos dois serviços; super-admin = coluna `is_super_admin` em `users`, ligada via SQL; guardar 30 dias ativos, depois arquivar, apagar com mais de 6 meses; corpo gravado com máscara · arquivo = tabela `request_logs_archive` no mesmo Postgres (mesmas colunas, `id bigint` sem serial para manter o id original, índice só em `at`), porque o deploy é uma VM única sem volume para arquivos · colunas: `id bigserial`, `at timestamptz`, `service` (`backend`|`gameServer`), `method`, `path` (só `r.URL.Path`, a query string nunca é gravada), `route` (padrão do chi, ex. `/getTicket/{RoomId}`), `status`, `duration_ms`, `ip`, `user_agent`, `user_id uuid null`, `username`, `request_id`, `body text null` (até 4 KB), `error text null` · usuário no log: o RequestMiddleware (que roda antes do auth) põe um ponteiro `*ReqInfo{UserID, Username}` no contexto antes do `next`; o middleware JWT do backend e o `JWTBackendMiddleware` do gameServer preenchem esse ponteiro; depois do `next` o RequestMiddleware lê o ponteiro e `chi.RouteContext(r.Context()).RoutePattern()` · captura do corpo: lê no máximo 64 KB com `io.LimitReader` e devolve ao handler com `io.NopCloser(io.MultiReader(bytes.NewReader(lido), r.Body))`; ordem: parsear JSON → mascarar → re-serializar → cortar em 4 KB; JSON inválido, não-JSON ou acima de 64 KB grava só `<N bytes>` · máscara: cabeçalho `Authorization` nunca é gravado; chaves do corpo que contêm (sem diferenciar maiúsculas) `token`, `ticket`, `password`, `senha`, `secret`, `authorization`, `apikey`, `api-key`, `credential`, `jwt` viram `"***"` em qualquer profundidade; `error` passa pela mesma máscara · não registra `/alive` nem nada em `/internal/*` (ruído, loop e chamadas gameServer→backend que duplicariam cada `/getTicket`); `/bugReports` (plano 05) grava só o tamanho do corpo · gravação assíncrona: canal com buffer de 1000 e lote a cada 2s ou 100 linhas; canal cheio descarta, e a cada 1 min com descarte > 0 loga `requestlog dropped=N`; no SIGTERM drena o canal e grava o último lote (timeout 3s) · gameServer junta o lote e manda em `POST /internal/requestLogs` (API key); a máscara existe nos dois módulos (cópia com teste nos dois) e o backend mascara de novo no ingest · ingest: `http.MaxBytesReader` 2 MB, até 500 linhas, campos cortados no servidor (`path` 512, `user_agent` 256, `username` 64, `body` 4096, `error` 1024), `service` forçado para `gameServer`, `at` fora de `now() ± 24h` vira `now()` · IP vem do `ClientIP` do plano 03 · retenção: job a cada hora no backend; numa transação, `pg_try_advisory_xact_lock(<const>)` primeiro (false → sai sem erro); move em lotes de 10.000 com `WITH d AS (DELETE FROM request_logs WHERE id IN (SELECT id FROM request_logs WHERE at < now() - interval '30 days' LIMIT 10000) RETURNING *) INSERT INTO request_logs_archive SELECT * FROM d` até acabar; depois apaga do arquivo `at < now() - interval '6 months'`; flag `-run-retention-once` roda uma vez e sai · API admin: `GET /admin/requestLogs` → `{items, total, page, limit}`, filtros `from`, `to`, `route` (contém), `status` (`^[1-5]xx$` ou inteiro 100–599), `userId` (UUID, senão 400), `username` (contém), `service` (`backend|gameServer`), `ip` (exato, validado com `net.ParseIP`, para seguir um suspeito de trapaça; IP inteiro também no arquivo, decisão do usuário), `archived=true`, `page` (1–1000), `limit` (máx. 200), ordem `at desc`; tudo por placeholder do gorm, com `%`, `_` e `\` escapados no LIKE (`ESCAPE '\'`), `route`/`username` até 64 caracteres; intervalo máximo de 31 dias (183 com `archived=true`); sem `from`/`to`, últimas 24h; `statement_timeout` de 5s · middleware `SuperAdmin` consulta `users.is_super_admin` a cada request (não vai no JWT) → 403 · tela: âncora `#admin` no app atual (mesmo padrão de `HASH_SCENES`), sem link no menu; tudo que vem da API é exibido como texto (`{valor}` ou `<pre>`), `dangerouslySetInnerHTML`/`innerHTML` proibidos em `features/admin` · schema de produção: além da migration goose, o `001_init.sql` do chart ganha `CREATE TABLE IF NOT EXISTS` / `ADD COLUMN IF NOT EXISTS`; migrations só aditivas (a imagem antiga ignora o que é novo, então o rollback não quebra) · Revisado em 2026-11-07: 19 correções aplicadas.
Pré-requisitos: plano 03 concluído (`ClientIP`); Postgres local (`make infra-up`); referência de UI: `D:\BUSINESS\SummusBackoffice\apps\server\internal\modules\audit-logs\docs\manual\tela-auditoria.md` (layout da tela de auditoria do Summus) com os tokens do Hoodwink (`client/web/src/styles`)

## Riscos
- Corpo com dado pessoal (email no login local) fica 6 meses → máscara cobre segredos; email documentado no T9
- Volume: health checks e chamadas internas inflariam a tabela → `/alive` e `/internal/*` fora; índice em `at` mantém a retenção barata
- Wrapper do ResponseWriter quebrar o upgrade do WebSocket → `Hijack`/`Flush` com teste no T5 e partida completa no aceite
- Banco fora do ar enchendo memória → canal limitado em 1000, descarta e loga a contagem
- Primeira execução da retenção com muito volume → lotes de 10.000 dentro da transação
